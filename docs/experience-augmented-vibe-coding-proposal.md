# 面向 Vibe Coding 的前端产品化经验抽取与 Skill 化注入机制研究

## 1. 课题背景

随着大语言模型和智能编码 Agent 的发展，Vibe Coding 正在成为一种新的软件开发方式。用户可以通过自然语言描述产品想法，由 Agent 完成需求澄清、方案设计、代码实现、测试修复等工作。这种方式降低了软件开发门槛，也显著提升了原型开发效率。

但是，当前 Vibe Coding 在真实产品开发中仍然存在明显局限：Agent 往往能够实现用户显式提出的功能，却容易忽略用户没有说清楚、甚至用户自己也不知道需要提出的产品化细节。例如，在前端开发中，用户可能只说「需要一个数据列表页」，Agent 可以生成列表展示和筛选功能，但未必会处理大数据量渲染、异步请求状态、失败重试、空状态、旧请求覆盖新响应、移动端布局溢出等问题。

这些问题并不一定属于功能缺失，却会直接影响产品的可用性、鲁棒性、性能和可维护性。它们通常来自工程实践中的隐性经验：成熟团队和企业级项目会在长期开发中沉淀出稳定的处理模式，而普通用户在提出需求时不会显式表达这些模式。Agent 如果缺少这些经验，就容易生成「功能能跑，但质量停留在 toy product」的结果。后续即使可以继续修补，也容易导致代码结构恶化，增加维护成本。

因此，本课题关注的问题不是如何让 Agent 写出更多代码，而是如何让 Agent 在 Vibe Coding 过程中主动获得并使用前端产品化经验，从而补全需求中的 unknown unknowns。

## 2. 研究目标

本课题拟研究一种面向 Vibe Coding 的经验检索与注入机制。该机制从成熟开源前端项目中抽取产品化质量经验，将其结构化为可检索、可复用、可阶段化注入的 Experience Units，并进一步包装为 Skill，使 Agent 在开发过程中能够按需调用相关经验，而不是将大量经验粗暴塞入 Prompt。

本课题的目标包括：

1. 建立一套从成熟开源前端项目中抽取产品化经验的方法。
2. 设计 Experience Unit 的结构化表示，覆盖触发场景、隐性风险、成熟实践、反模式、注入方式和验收标准。
3. 设计一种低干扰、高可执行的 Skill 化注入机制，使 Agent 能够根据当前任务上下文检索少量相关经验。
4. 以前端产品化质量为主要场景，验证该机制是否能够提升 Agent 生成应用的完整性、鲁棒性和可维护性。

## 3. 核心研究问题

本课题聚焦 3 个核心问题。

### 3.1 如何从成熟开源前端项目中抽取产品化经验？

成熟项目中的经验并不总是以文档形式存在，更多隐藏在代码结构、组件实现、工具封装、测试用例、Issue 和 Pull Request 讨论中。本课题需要研究如何从这些材料中识别可迁移的工程经验，而不是简单复制代码片段。

经验抽取的目标不是获得「某个项目怎么写」，而是抽象出「在某类前端场景中，成熟项目为什么会这样处理」。

### 3.2 如何以低干扰、高可执行的形式注入经验？

如果将所有经验一次性加入 Prompt，会带来上下文膨胀、注意力分散、无关约束干扰等问题。本课题需要研究如何根据当前任务、技术栈、开发阶段和代码上下文，选择最相关的少量经验，并以 Agent 能直接执行的形式注入。

注入内容不应停留在「注意性能」「处理错误」这类泛泛提醒，而应转化为具体的计划要求、实现约束、Review 检查项或测试建议。

### 3.3 如何将经验机制包装为可复用 Skill？

Skill 是一种适合 Agent 使用的知识与流程封装形式。它可以定义触发条件、读取规则、检索方式和执行约束。本课题拟将前端产品化经验包装为一个 `frontend-productization` Skill。该 Skill 不直接加载所有经验，而是充当 Experience Router，根据上下文选择相关 Experience Units 并注入到当前阶段。

## 4. 研究范围

本课题第一阶段聚焦前端产品化质量，不覆盖完整全栈工程经验。

重点覆盖以下场景：

1. 异步请求状态：loading、error、empty、retry、取消过期请求。
2. 列表渲染性能：分页、懒加载、虚拟列表、大数据量渲染。
3. 表单鲁棒性：校验、防重复提交、提交中状态、失败恢复。
4. 状态一致性：乐观更新、旧请求覆盖、新旧数据同步。
5. 错误与空状态体验：错误边界、fallback UI、空数据提示。
6. 响应式与布局边界：移动端适配、长文本溢出、容器尺寸变化。

暂不覆盖：

1. 后端架构经验。
2. 数据库设计经验。
3. DevOps、部署和监控经验。
4. 安全合规经验。
5. 完整 Vibe Coding 工作流系统。

## 5. 技术路线

本课题的整体技术路线如下：

```text
成熟开源前端项目
-> 代码与变更历史分析
-> 产品化经验抽取
-> Experience Unit 结构化表示
-> Skill 化索引与路由
-> 阶段化注入
-> Vibe Coding 对比实验
```

### 5.1 数据来源

经验来源选取成熟、长期维护、具有真实产品场景的开源前端项目。候选项目包括：

1. Kibana：大型 TypeScript 前端系统，适合分析复杂状态、插件化架构、错误处理和数据可视化性能经验。
2. react-admin：面向后台管理系统和 CRUD 应用，适合分析列表、表单、数据请求、权限和资源模型经验。
3. refine：面向 internal tools 和 dashboard 场景，适合分析数据获取、表单、路由、mutation 和缓存经验。
4. GitLab 前端代码与文档：适合分析大型协作平台中的前端组件规范和产品化实践。

第一阶段建议选择 3 个主样本项目，避免样本过多导致抽取成本失控。

### 5.2 经验抽取流程

经验抽取分为 3 个层次。

#### 5.2.1 静态代码模式分析

从项目代码中识别反复出现的前端产品化处理模式，例如：

1. 统一请求封装或 data provider。
2. 组件中的 loading、error、empty 状态分支。
3. 分页、无限滚动、虚拟列表等列表性能策略。
4. 表单校验、提交中状态、防重复提交。
5. Error Boundary 和 fallback UI。
6. 响应式布局、可访问性属性、长文本处理。

#### 5.2.2 Issue / Pull Request 挖掘

许多经验来自 bug 修复和代码评审，而不是最终代码本身。本课题将分析成熟项目中的 Issue、Pull Request 和 commit message，重点关注以下类型的问题：

1. 请求竞态导致旧响应覆盖新状态。
2. 大列表或复杂图表导致页面卡顿。
3. 异步失败时界面无反馈。
4. 表单重复提交导致重复数据。
5. 空数据、异常数据导致页面崩溃。
6. 小屏幕、长文本、极端输入导致布局错乱。

这些问题可以帮助提炼「为什么需要某条经验」。

#### 5.2.3 人工蒸馏与归纳

抽取结果最终不保存为代码片段，而是归纳为 Experience Unit。每条经验需要回答：

1. 什么任务场景会触发这条经验？
2. 如果忽略它，会出现什么隐性风险？
3. 成熟项目通常如何处理？
4. 常见的 toy product 反模式是什么？
5. 在 Plan、Coding、Review、Test 阶段应如何注入？
6. 如何验证 Agent 是否真正应用了该经验？

## 6. Experience Unit 设计

Experience Unit 是本课题的核心知识表示单位。建议采用 Markdown 或 YAML Front Matter 加正文的形式，兼顾机器可检索和人工可维护。

示例结构如下：

```yaml
id: async-request-state
title: 异步请求必须显式建模用户可感知状态
category: frontend-productization
tags:
  - async
  - request
  - loading
  - error
  - empty-state
triggers:
  - 页面需要从 API 加载数据
  - 用户操作会触发异步请求
  - 列表、详情、搜索、筛选依赖远程数据
risk:
  - 慢请求期间界面无反馈
  - 请求失败后用户不知道如何恢复
  - 空数据被误认为加载失败
anti_patterns:
  - 组件只处理 success path
  - 请求失败只在 console 中打印错误
  - loading 和 empty 状态混用
injection:
  plan: 计划中必须定义 loading、error、empty 和 retry 行为。
  coding: 实现时将异步状态建模为明确状态机或等价结构。
  review: 检查是否存在只处理成功响应的组件。
  test: 增加慢请求、失败请求和空数据场景测试。
verification:
  - 慢请求时界面有 loading 或 skeleton
  - 请求失败时展示可恢复错误状态
  - 空数据时展示明确 empty state
evidence:
  - source: react-admin
    note: 多数数据视图显式处理 loading 与 error 状态
```

这种结构使经验可以被索引、检索和阶段化转换。

## 7. Skill 化注入机制

本课题拟设计一个 `frontend-productization` Skill。它不是一个静态 Prompt，而是一个经验路由器。

### 7.1 Skill 目录结构

建议结构如下：

```text
frontend-productization/
├─ SKILL.md
├─ experience-index.json
├─ experiences/
│  ├─ async-request-state.md
│  ├─ stale-response-control.md
│  ├─ large-list-rendering.md
│  ├─ form-submit-robustness.md
│  ├─ empty-error-loading-states.md
│  └─ responsive-overflow.md
└─ evidence/
   ├─ kibana/
   ├─ react-admin/
   └─ refine/
```

### 7.2 Skill 工作流程

Skill 的工作流程分为 4 步：

1. **识别上下文：** 判断当前任务是否涉及前端页面、列表、表单、异步请求、dashboard、admin 或 internal tool。
2. **检索经验：** 根据任务描述、计划草稿、代码结构和开发阶段，从 `experience-index.json` 中选择候选经验。
3. **限制注入数量：** 默认只注入 3 到 5 条最相关经验，避免上下文污染。
4. **阶段化转换：** 根据当前阶段，将经验转换为计划补充、实现约束、Review 检查项或测试建议。

### 7.3 阶段化注入形式

同一条经验在不同阶段的注入形式不同。

Plan 阶段：

```text
该功能涉及异步数据加载。计划中必须明确 loading、error、empty、retry 状态，并说明请求失败后的用户恢复路径。
```

Coding 阶段：

```text
实现请求逻辑时，避免旧响应覆盖新状态。可以使用 AbortController、request id 或等价机制处理请求竞态。
```

Review 阶段：

```text
检查该页面是否只实现 success path。若缺少 loading、error、empty 或 retry 状态，应视为产品化质量缺陷。
```

Test 阶段：

```text
增加慢请求、失败请求、空数据、快速切换筛选条件等测试场景。
```

这种方式可以让 Agent 获得可执行指令，而不是接收抽象提醒。

## 8. 系统架构

本课题系统可分为离线经验构建和在线经验注入两部分。

### 8.1 离线经验构建

离线部分负责从成熟开源项目中抽取经验，主要包括：

1. 项目选择与样本确定。
2. 代码模式扫描。
3. Issue / Pull Request 挖掘。
4. 经验候选归纳。
5. Experience Unit 编写。
6. 经验索引构建。

离线构建可以半自动完成。模型可辅助总结候选经验，但最终需要人工审查，确保经验具有通用性、可执行性和证据来源。

### 8.2 在线经验注入

在线部分在 Vibe Coding 过程中运行，主要包括：

1. 接收当前任务上下文。
2. 判断当前开发阶段。
3. 检索相关 Experience Units。
4. 将经验转换为阶段化指令。
5. 将指令注入给 Agent。
6. 在 Review 或 Test 阶段检查经验是否被落实。

该机制可以作为独立 Skill 嵌入到 Cursor、Codex 或其他支持 Skill / instruction 文件的 Agent 环境中。

## 9. 实验设计

本课题拟通过对比实验验证经验注入机制的有效性。

### 9.1 实验任务

选取若干典型前端开发任务，例如：

1. 构建一个带搜索和筛选的数据列表页。
2. 构建一个包含异步校验和提交的表单页。
3. 构建一个 dashboard 数据概览页。
4. 构建一个支持移动端的管理后台页面。

每个任务都设计基础功能需求，但不显式提醒产品化细节。例如，不主动告诉 Agent 需要处理 loading、error、empty、分页、防重复提交等问题。

### 9.2 实验组设置

设置两个主要实验组：

1. **Baseline 组：** Agent 只接收普通用户需求。
2. **Experience Skill 组：** Agent 在相同需求下使用 `frontend-productization` Skill 进行经验检索与注入。

如时间允许，可增加第三组：

3. **Full Prompt 组：** 将完整经验 checklist 直接放入 Prompt，用于对比 Skill 化检索是否比粗暴注入更低干扰。

### 9.3 评价指标

评价指标分为功能质量、产品化质量和代码质量。

功能质量：

1. 是否完成用户显式提出的功能。
2. 功能路径是否可运行。

产品化质量：

1. 是否处理 loading、error、empty 状态。
2. 是否处理异步竞态和失败恢复。
3. 是否避免大列表一次性渲染。
4. 是否处理表单重复提交和校验反馈。
5. 是否处理响应式布局和长文本边界。

代码质量：

1. 组件边界是否清晰。
2. 请求逻辑是否集中或可复用。
3. 状态建模是否清楚。
4. 测试是否覆盖边界场景。
5. 后续修改是否容易引入结构性混乱。

可以将上述指标设计为评分表，由人工评审和自动检查结合完成。

### 9.4 预期实验假设

本课题预期验证以下假设：

1. 使用 Experience Skill 的 Agent 比 Baseline 更容易补全用户未显式提出的产品化细节。
2. Skill 化检索比完整 checklist 注入更低干扰，生成结果更聚焦。
3. 阶段化注入比单次 Prompt 注入更容易转化为代码、测试和 Review 行为。

## 10. 预期成果

本课题预期产出以下成果：

1. 一套从成熟开源前端项目中抽取产品化经验的方法。
2. 一个前端产品化 Experience Unit schema。
3. 一批前端产品化经验样例库，初期规模约 20 条。
4. 一个 `frontend-productization` Skill 原型。
5. 一套用于 Vibe Coding 质量对比的实验任务和评价指标。
6. 一份实验报告，分析经验注入对 Agent 生成质量的影响。

## 11. 创新点

本课题的创新点主要体现在两个方面。

第一，研究对象不是代码片段复用，而是产品化质量经验的抽取。传统代码生成更关注如何根据需求生成实现，本课题关注成熟项目中隐含的工程判断和产品质量模式，并将其抽象为可迁移的经验单元。

第二，注入方式不是粗暴扩展 Prompt，而是通过 Skill 进行检索式、阶段化注入。Skill 只在相关场景读取少量经验，并根据 Plan、Coding、Review、Test 阶段转化为不同形式的可执行约束，从而降低上下文干扰，提高 Agent 对经验的实际利用率。

## 12. 风险与应对

### 12.1 经验抽取主观性较强

风险：从代码和 Issue 中归纳经验可能受到研究者主观判断影响。

应对：每条 Experience Unit 保留 evidence 字段，记录来源项目、文件、Issue 或 Pull Request，并通过人工复核提高可信度。

### 12.2 经验过多导致 Skill 使用成本上升

风险：经验库规模扩大后，检索和维护成本增加。

应对：第一阶段限制经验库规模，优先覆盖高频前端产品化问题。Skill 默认只注入 3 到 5 条经验。

### 12.3 实验评价可能依赖人工判断

风险：产品化质量难以完全自动评估。

应对：采用评分 Rubric，将人工评审与自动测试结合。可对 loading、error、empty、分页、防重复提交等明确指标进行自动或半自动检查。

### 12.4 不同 Agent 对 Skill 的遵循能力不同

风险：不同编码 Agent 对 Skill 文件、指令层级和工具调用能力支持不同。

应对：第一阶段优先在一个主要环境中验证，例如 Cursor 或 Codex。Skill 文件采用通用 Markdown 结构，降低迁移成本。

## 13. 阶段计划

### 第一阶段：问题定义与样本选择

明确研究范围，确定 3 个成熟开源前端项目作为主要样本，建立前端产品化质量分类。

### 第二阶段：经验抽取与 Schema 设计

分析项目代码、Issue 和 Pull Request，抽取第一批 Experience Units，并完善字段结构和证据记录方式。

### 第三阶段：Skill 原型实现

构建 `frontend-productization` Skill，包含 `SKILL.md`、经验索引、经验文件和阶段化注入模板。

### 第四阶段：实验任务设计

设计典型前端开发任务，建立 Baseline 组、Experience Skill 组和可选 Full Prompt 组。

### 第五阶段：实验评估与总结

运行对比实验，收集生成结果，按照功能质量、产品化质量和代码质量进行评估，分析经验注入机制的有效性。

## 14. 当前最小可行版本

MVP 建议聚焦以下内容：

1. 选取 2 到 3 个成熟开源前端项目。
2. 抽取 6 类前端产品化经验。
3. 每类沉淀 3 条 Experience Units，总数约 18 条。
4. 实现一个 `frontend-productization` Skill 原型。
5. 设计 3 个前端任务进行对比实验。

MVP 成功标准是：在相同用户需求下，使用 Skill 的 Agent 能明显更主动地处理异步状态、错误恢复、列表性能、表单鲁棒性和响应式边界，而不是只完成显式功能。
